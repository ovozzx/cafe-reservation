## 2. DB 스키마

### 설계 결정 사항

| 결정 | 내용 | 이유 |
|------|------|------|
| is_deleted 소프트 삭제 | users, orders, payment, seat에 is_deleted 추가. reservation, order_item, menu는 미적용 | reservation은 상태(EXPIRED 등)로 관리, menu는 is_available로 관리 |
| reserve_date 컬럼 제거 | reservation.reserve_date 제거 | start_time에서 날짜 추출 가능하므로 중복 |
| menu_id 타입 변경 | VARCHAR(20) → BIGINT AUTO_INCREMENT | 레거시 'MENU_1' 같은 문자열 ID를 숫자 PK로 정규화. 마이그레이션 시 데이터 변환 필요 |
| seat_row 타입 변경 | INT → VARCHAR(5) | 레거시 1,2,3 → 'L','R','W' 의미 있는 값으로 변경 |
| user_id 길이 | VARCHAR(20) → VARCHAR(50) | GUEST_{UUID} 형식 수용 |

### 최종 ERD

```
users (1) ──── (N) orders (1) ──── (N) order_item (N) ──── (1) menu
                      │
                      ├──── (1) payment
                      │
                      └──── (N) reservation (N) ──── (1) seat
```

```java
        return user;

        this.refreshToken = refreshToken;
    }

    public boolean isGuest() {
        return this.role == Role.GUEST;
    }
```

### Order
```java
@Entity
@Table(name = "orders")
public class Order extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long orderId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OrderType orderType;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private OrderStatus status;

    @Column(nullable = false)
    private int totalAmount;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();

    @OneToOne(mappedBy = "order", cascade = CascadeType.ALL)
    private Payment payment;

    @OneToMany(mappedBy = "order")
    private List<Reservation> reservations = new ArrayList<>();

    // === 비즈니스 메서드 === //

    public static Order create(User user, OrderType orderType, List<OrderItem> items) {
        Order order = new Order();
        order.user = user;
        order.orderType = orderType;
        order.status = OrderStatus.ORDERED;
        items.forEach(order::addItem);
        order.calculateTotalAmount();
        return order;
    }

    private void addItem(OrderItem item) {
        items.add(item);
        item.setOrder(this);
    }

    private void calculateTotalAmount() {
        this.totalAmount = items.stream()
                .mapToInt(item -> item.getPrice() * item.getQuantity())
                .sum();
    }

    public boolean isOwnedBy(String userId) {
        return this.user.getUserId().equals(userId);
    }

    public boolean isOrderExpired() {
        return this.getCreatedAt().plusMinutes(5).isBefore(LocalDateTime.now());
    }

    public void cancel() {
        if (this.status != OrderStatus.ORDERED) {
            throw new BusinessException(ErrorCode.ORDER_CANNOT_CANCEL);
        }
        this.status = OrderStatus.CANCELED;
    }

    public void startMaking() {
        this.status = OrderStatus.MAKING;
    }

    public void complete() {
        this.status = OrderStatus.DONE;
    }

    public boolean isDineIn() {
        return this.orderType == OrderType.DINE_IN;
    }
}
```

### Reservation
```java
@Entity
@Table(name = "reservation")
public class Reservation extends BaseTimeEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long reservationId;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "order_id", nullable = false)
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "seat_id", nullable = false)
    private Seat seat;

    @Column(nullable = false)
    private LocalDateTime startTime;

    @Column(nullable = false)
    private LocalDateTime endTime;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private ReservationStatus status;

    public static Reservation createTemp(Order order, Seat seat, int hours) {
        Reservation reservation = new Reservation();
        reservation.order = order;
        reservation.seat = seat;
        reservation.startTime = LocalDateTime.now();
        reservation.endTime = LocalDateTime.now().plusHours(hours);
        reservation.status = ReservationStatus.TEMP;
        seat.reserve();  // 좌석 상태도 함께 변경
        return reservation;
    }

    public void confirm() {
        this.status = ReservationStatus.CONFIRMED;
        this.seat.confirm();
    }

    public void expire() {
        this.status = ReservationStatus.EXPIRED;
        this.seat.release();
    }
}
```

```java
    private PaymentStatus status;

    @Column(length = 30)
    private String payMethod;

    public static Payment create(Order order) {
        Payment payment = new Payment();
        payment.order = order;
        payment.merchantUid = "ORD-" + UUID.randomUUID();
        payment.amount = order.getTotalAmount();
        payment.status = PaymentStatus.READY;
        return payment;
    }

    public void markPaid(String impUid, String payMethod) {
        if (this.status == PaymentStatus.PAID) {
            throw new BusinessException(ErrorCode.PAYMENT_ALREADY_PAID);
        }
        if (this.status != PaymentStatus.READY) {
            throw new BusinessException(ErrorCode.PAYMENT_NOT_READY);
        }
        this.impUid = impUid;
        this.payMethod = payMethod;
        this.status = PaymentStatus.PAID;
    }

    public void markFailed() {
        this.status = PaymentStatus.FAILED;
    }
}
```

### 비회원(GUEST) 처리 전략

```
레거시에서 비회원 주문은 두 가지 흐름이 있었음:
1. 포장 주문 → userId를 "GUEST"로 하드코딩 (한 계정에 모든 비회원 주문)
2. 먹고가기 비회원 → "GUEST_" + UUID로 고유 계정 생성

리팩터링에서는 통일:
- POST /api/auth/guest 호출 시 "GUEST_{UUID}" 계정을 매번 새로 생성
- role = GUEST, Access Token만 발급 (Refresh Token 미발급)
- 비회원은 주문 생성, 결제만 가능 (주문 이력 조회 불가)
- 미사용 GUEST 계정은 배치로 주기적 정리 (향후 구현)
```

## 6. JWT 인증

### 토큰 스펙

| | Access Token | Refresh Token |
|------|-------------|---------------|
| 만료 | 30분 | 7일 |
| 저장 (클라이언트) | localStorage | localStorage |
| 저장 (서버) | X (Stateless) | users.refresh_token |
| Payload | sub(userId), role, iss, iat, exp | sub(userId), iss, iat, exp |
| 비회원 | 발급 O | 발급 X |

### 보안 정책

| 정책 | 설명 |
|------|------|
| Refresh Token Rotation | 갱신 시마다 새 Refresh Token 발급 + DB 교체 + 이전 토큰 무효화 → 탈취 시 피해 최소화 |
| 비회원 토큰 | Access Token만 발급 (30분), Refresh Token 미발급 → 만료 후 새로 발급 |
| 로그아웃 | Refresh Token 기반 → AT 만료 상태에서도 로그아웃 가능 (logout은 permitAll) |
| AT 블랙리스트 | 미적용 (30분 만료 수용). 필요 시 Redis 도입 가능 |
| XSS | 카페 키오스크 환경이므로 localStorage 사용. 일반 웹이라면 HttpOnly Cookie 권장 |

### 인증 흐름
```
[로그인]
POST /api/auth/login → Access Token + Refresh Token 발급
                        → Refresh Token은 DB에도 저장

[API 호출]
Header: Authorization: Bearer {accessToken}
→ JwtAuthenticationFilter에서 검증 → SecurityContext 설정

[토큰 갱신 (Rotation)]
POST /api/auth/refresh (refreshToken)
→ DB의 refreshToken과 비교 → 일치 시 새 AT + 새 RT 발급 → DB 교체
→ 불일치 시 401 (탈취 의심 → 해당 유저 RT 전체 무효화)

[로그아웃]
POST /api/auth/logout (refreshToken)
→ DB에서 Refresh Token 삭제 (permitAll이므로 AT 만료 상태에서도 가능)

[비회원]
POST /api/auth/guest → GUEST_{UUID} 계정 생성 + Access Token만 발급
```

## 7. 핵심 비즈니스 흐름

### 먹고가기 (DINE_IN)
```
시작 페이지 → 로그인 (또는 비회원 토큰) → 메뉴 선택 (클라이언트 장바구니)
→ POST /api/orders (주문 생성 + Payment READY) ← 5분 타이머 시작 (order.createdAt 기준)
→ GET /api/seats (좌석 조회)
→ POST /api/orders/{id}/reservations (좌석 TEMP 예약) ← 서버에서 5분 제한 검증
→ GET /api/orders/{id} (주문 요약)
→ GET /api/orders/{id}/payment/prepare (결제 준비)
→ 아임포트 결제 모달
→ POST /api/orders/{id}/payment/validate (결제 검증)
  → 성공: Payment→PAID, Reservation→CONFIRMED, Seat→RESERVED
  → 실패: Payment→FAILED, Reservation/Seat는 스케줄러가 5분 후 TEMP 만료 처리
```

### 포장하기 (TAKEOUT)
```
시작 페이지 → 비회원 토큰 발급 (또는 로그인) → 메뉴 선택 (클라이언트 장바구니)
→ POST /api/orders (orderType=TAKEOUT)
→ GET /api/orders/{id} (주문 요약, 좌석 없음)
→ 결제 흐름 동일
```

### 결제 실패 시 좌석 처리 전략
```
결제 실패 → Payment만 FAILED로 변경
좌석/예약 → 즉시 롤백하지 않음 (스케줄러가 TEMP 5분 만료 시 자동 해제)
이유: 사용자가 재결제를 시도할 수 있으므로, 좌석을 즉시 풀면 다른 사용자에게 뺏길 수 있음
```

### 5분 주문 시간 제한
```
레거시: 세션 orderStartTime 기반 서버 검증
리팩터링: order.createdAt 기준 서버 측 검증

검증 시점:
1. POST /api/orders/{id}/reservations → order.isOrderExpired() 체크
2. POST /api/orders/{id}/payment/validate → order.isOrderExpired() 체크
→ 초과 시 ORDER_TIME_EXPIRED (400) 반환

클라이언트: 주문 생성 응답의 createdAt으로 카운트다운 타이머 표시
```

### 스케줄러 (1분마다)
```
@Scheduled(cron = "0 * * * * *")
1. 예약 만료: end_time < NOW() AND status IN (TEMP, CONFIRMED)
   → Reservation→EXPIRED, Seat→AVAILABLE

2. TEMP 만료: created_at + 5분 < NOW() AND status = TEMP
   → Reservation→EXPIRED, Seat→AVAILABLE

동시성 처리: fetch join으로 Seat과 함께 조회, 엔티티 메서드로 상태 변경
→ 사용자 예약과 스케줄러의 경합은 비관적 락(findByIdForUpdate)으로 해결
```

### 트랜잭션 경계
```
1. 주문 생성 (OrderService.createOrder)
   @Transactional: Order INSERT + OrderItem INSERT + Payment INSERT

2. 좌석 예약 (ReservationService.reserveSeats)
   @Transactional: Seat 비관적 락 조회 + Reservation INSERT + Seat 상태 변경

3. 결제 검증 (PaymentService.validatePayment)
   트랜잭션 밖: IamportClient로 외부 API 호출 (결제액 조회)
   @Transactional: Payment 상태 변경 + (성공 시) Reservation/Seat 상태 변경

4. 스케줄러 (ReservationScheduler)
   @Transactional: 만료 대상 벌크 조회 + 상태 변경
```

| 9 | 마무리 | Swagger 문서화, 테스트 코드, README |

### Phase 의존성 설명
```
Phase 4에서 Payment 엔티티를 함께 구현하는 이유:
→ 주문 생성(POST /api/orders) 시 Payment도 READY 상태로 함께 생성
→ Payment 엔티티 없이는 주문 생성 불가

Phase 5(좌석)와 Phase 6(예약)을 분리하는 이유:
→ 좌석은 단순 조회 + 상태 관리
→ 예약은 복잡한 비즈니스 로직 (TEMP, 동시성, 스케줄러)
→ 리스크 관리를 위해 분리

Phase 7에서 결제 검증만 분리하는 이유:
→ IamportClient (외부 API), 결제 검증 로직, 트랜잭션 경계 설계가 복잡
→ 엔티티(Phase 4)와 비즈니스 로직(Phase 7)을 분리
```

## 11. 포트폴리오 어필 포인트

| 항목 | 레거시 문제 | 리팩터링 해결 |
|------|-----------|-------------|
| 인증 | 세션 (서버 메모리, 수평 확장 불가) | JWT Stateless + Refresh Token Rotation |
| 비밀번호 | SHA-256 + Salt (직접 구현) | BCrypt (업계 표준, Spring Security 내장) |
| API | 뷰 반환 + AJAX 혼재 | REST API 완전 분리 + Swagger 문서화 |
| 데이터 접근 | MyBatis SQL 직접 작성 | JPA 객체 중심 + Spring Data Repository |
| 예외 처리 | JSP 에러 페이지 | 에러 코드 체계 + JSON 응답 (도메인별 분류) |
| 검증 | 수동 if 분기 | Bean Validation 선언적 검증 |
| 엔티티 | VO에 로직 없음 (빈약한 도메인) | 엔티티에 비즈니스 메서드 (도메인 주도) |
| 가격 정합성 | 메뉴 가격 변경 시 과거 주문 영향 | OrderItem에 주문 시점 가격 스냅샷 |
| 결제 보안 | orderId를 merchantUid로 직접 사용 | UUID 기반 merchantUid (식별자 노출 방지) |
| 외부 API | Service에 아임포트 호출 코드 혼재 | IamportClient + IamportProperties로 분리 |
| 테스트 | 없음 | JUnit 5 + Mockito 단위 테스트 |
| 동시성 | SQL FOR UPDATE 직접 작성 | JPA @Lock(PESSIMISTIC_WRITE) + Repository 메서드 |
| N+1 | N/A (MyBatis JOIN) | fetch join + 컬렉션 분리 조회 전략 |
| 트랜잭션 | @Transactional 단순 적용 | 외부 API 호출은 트랜잭션 밖, DB 변경만 트랜잭션 안 |
| 주문 시간 | 세션 기반 서버 검증 | 엔티티 메서드 (order.isOrderExpired()) |
